Hallo-Live: test a spoken-scene model, not a turnkey client

The two-H200 paper reports 20.38 generated FPS. Its public inference command saves a 24-fps file, above the paper throughput, and a maintainer estimates about 60 GB peak GPU memory for default inference. Treat 24 GB as a theoretical target, not a setup recommendation. Read the pre-spend test.

LiveAvatar: choose clip or conversation

Authors report: five H100s, 45.2 generated FPS and 1.21 seconds from audio arrival to first visual output at 720×400. They estimate roughly three seconds with transport. The released one-GPU command is offline; an independent H200 cold finished clip took 181.44 seconds. Do not price a live conversation from that clip. Read the route and clock check.

ShotStream is a research route, not a packaged live client

Paper reports: 15.95 generated FPS at 832×480 on one H200 for multi-shot stories. The public example reads prepared prompts from a CSV and writes a final MP4. Use the reference checkpoint for a bounded offline study; do not choose it as a viewer-ready live setup without a prompt-change and receiver test. Read the boundary.

Decision guide · checked 7 October 2026

Choose the control and deployment contracts, then test the claim

A model name does not tell you whether you are buying a group-choice loop, an interactive session, a remote GPU service, a clip queue, an unattended local channel, or a short local render.

New watchlist: Tavus Griffin-Lite

It is a selected-tester research preview for full-duplex face-to-face video. Tavus reports 0.43-second audio-to-video generator latency on H100s, not a customer session. No Griffin-specific customer price or public route is documented. Read the access and timing check.

Veda: test a faster offline H3 clip

The project reports a complete 5.17-second H3 T2VA clip in 130.1 seconds on one RTX 5070 with Veda, versus 342.1 seconds on its default ComfyUI path. This is a viable acceleration experiment, not a consumer live-video route. Match task, version, output and quality before switching. Read the timing card.

Pick remote serving when

You need the creator UI and the H3 machine to be different systems, or you want several clients to reuse one service. vLLM-Omni’s current H3 recipe records an OpenAI-compatible route. Its current H3 API/ComfyUI RFC says the server and current client have different input limits: check that the client can send the needed keyframes or references. The recipe documents one two-RTX-5090, 50-step T2VA job at 1344×768: 124 frames at 24 fps, about 5.17 seconds of output, returned in 8 minutes 38 seconds. The current two-GPU launch selects the FL2VA path, which serves T2VA and FL2VA, and recommends a 384 GiB host. That is an offline capacity lead. A separate eight-B300 FastH3 T2VA report says a complete 10.125-second MP4 returns in 8.678–8.710 seconds after warmup. Keep the two rows separate.

Pick an offline two-5090 H3 test when

You need one controlled T2VA or FL2VA render and can supply server-class host memory, storage, and a long returned-artifact wait. The published DLO launch selects FL2VA; the documented record is still T2VA only. Validate a first/last-frame request and a second queued request before renting or buying for a continuity product.

Do not sell a queue with a scheduler flag

Project says: its stated two-H100 H3 test submitted four jobs at once. Four-way co-batching took longer than ordinary request mode. The source leaves staggered arrivals unmeasured. State the arrival pattern, job shape, concurrency, first playable media, and fallback before you call the route responsive.

Pick a group-choice loop when

You want participation to create anticipation for the next scene instead of a viewer controlling the current one. Yoroll’s launch announcement says YoLive uses proposals and votes. The stated generation time is fast, but do not choose the route until you know the selection rule, moderation delay, response time, delivery behavior, and cost.

Pick Dreamverse when

You need a published FastH3 application design that tries to carry a visual boundary forward rather than merely play distinct ready clips. The current Dreamverse README calls for four visible GPUs by default. Treat it as a four-GPU evaluation route: time the cold readiness state, then inspect a warm handoff before you write a continuity promise.

Pick Director when

You need the product shape of an open session. The current provider page says it streams through WebRTC and carries context into later directions. Plan for a finite session from the first sketch, and price $4.80 for even the stated 60-second minimum.

RAVEN on a 24-GiB card: not yet demonstrated

The maintainer's 192-frame record ran on an H200 with 24.100 GiB left free, not on a physical 24-GiB GPU. It used synthetic conditioning. A separate 39-frame real-prompt test ran without the memory limit. The maintainer advises 160 GiB available host RAM and verified ComfyUI 0.33.0. Do not choose hardware or promise live playout from the 24-GiB headline. Read the claim check.

Baseline card before you spend a weekend

  1. Write who can propose, who selects, what changes, and whether the active scene can change.
  2. State client host, inference host, task, adapter load point, server revision, GPU, host memory, and any carried conditioning frame.
  3. Record cold, warm, accepted-input, ready, HTTP response, delivered-start, and visible-change timestamps.
  4. For a channel or queue, record ready clips, playback speed, filler, retries, and black or silent fallback.
  5. Label the result as provider documentation, project report, community report, or a measured test. Do not blend them.

Sources: vLLM-Omni FastH3 serving report, vLLM-Omni H3 recipe, Yoroll’s YoLive announcement, fal Director documentation, Reactor FastH3 README, and the FastH3 Live community project, and FastVideo’s Dreamverse README.
